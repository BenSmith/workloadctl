# 10. Troubleshooting

This chapter starts with the commands that tell you what is wrong, then
lists problems by area: each entry names what you see, what causes it, and
what to do. Most entries end in a `workloadctl` command rather than a manual
repair, because the commands redo every step a repair needs, in order.

## A first look

### Status and logs

```bash
workloadctl status <name>
workloadctl logs <name>
workloadctl logs -f <name>
```

`logs` shows the last 50 lines of everything the workload wrote: the
messages podman and systemd logged while starting and stopping it, and the
output of its containers. Anything after the workload name is passed to
`journalctl`, so `workloadctl logs <name> -b -p err` works.

Use `logs` rather than `journalctl -u workload-<name>.service`, which shows
only the start and stop lines and podman's own messages: the journal files a
container's output under the workload user's systemd manager, not under the
unit. `podman logs` does not work at all, because podman keeps no copy.
[Logs](09-operating.md#logs) explains how to select a workload's lines with
`journalctl` directly.

For a VM, `logs` shows QEMU's messages and workloadctl's, not the guest's.
Read the guest's own journal from inside it:

```bash
sudo workloadctl exec <name> -- journalctl -b -p warning
```

### doctor: everything at once

```bash
sudo workloadctl doctor <name>
```

`doctor` gathers what you would otherwise collect by hand and prints it in
one report. It changes nothing. It exits 0 when it finds no problem and 1
when it finds one, including when the workload's TOML cannot be loaded at
all, in which case it prints why in one line.

The report reads top to bottom:

- **The header** names the workload's substrate, mode, lifecycle and whether
  it is enabled. `[stale — edited since last enable]` beside the config path
  means the TOML is newer than the units generated from it. A `Units:` line
  saying they were generated by another version means the package was
  upgraded and the workload has not been set up since.
- **Generator (this boot)** shows the lines the boot-time generator logged
  about this workload. A line containing "error" is a reason it was skipped.
- **Units** lists every unit the workload has, in the order they start, with
  its state. A unit that has failed, is stuck in `activating`, or has
  restarted at all (`NRestarts`) is marked, and the last 15 lines of its
  journal are printed under it. A unit that keeps restarting never reaches
  `failed`, so the restart count is often the only sign.
- **Setup checks** is the `diagnose` battery below, with only the failures
  and the warnings printed. A warning is marked `!` and has its `Fix:` under
  it; when nothing failed, the section is `✓ N checks passed` followed by
  any warnings.
- **Drift** says whether the units in `/run/systemd/system` still match what
  the TOML would generate now.
- **Health** says whether the service is active and its containers are
  running.
- **Egress (inspected)**, for a filtered workload, carries the inspector's
  counters. They are evidence, not a verdict: refusals are the filter
  working, so none of them count as a problem.

The last line is `Overall: HEALTHY` or `Overall: UNHEALTHY (N problems)`.
A warning is not a problem, so a workload with one reads `Overall: HEALTHY (1
warning)` and the command still exits 0. `--json` prints the whole report as
one object, with the number of warnings in `overall.warnings`.

### diagnose: what is wrong with this host's setup

```bash
sudo workloadctl diagnose <name>
```

`diagnose` runs the setup checks on their own and prints each one: `✓` for
a pass, `!` for a warning and `✗` for a failure, the last two with a `Fix:`
line under them. At the end it prints a numbered list of the failures and
their fixes, then one of the warnings. A warning is a check that passed and
that you should still see. It counts as passed, so it never fails the
command or changes its exit status: the summary reads `Checks: 12/12 passed,
1 warning`, and the last line `✓ All checks passed (1 warning) - workload is
healthy`. `diagnose` exits 1 if any check failed. `--json` prints each check
as `{check, passed, message, fix}`, adds `"warning": true` to a warning, and
counts the warnings in the top-level `checks_warned`. The `check` names below
are the ones it uses.

A check that cannot find out does not claim a pass: without `semanage`,
with SELinux disabled, or with `/etc/login.defs` unreadable, the checks that
depend on them say the state is unknown or are left out.

A disabled workload has, on purpose, no linger, no runtime directory and no
running units. `diagnose` folds those expected absences into one passing
line, `workload_disabled`, and goes on reporting what must stay right while
the workload is off: its labels, its ID ranges and its volume paths. A VM
uses no subordinate IDs and no user manager, so its battery skips the
checks that concern them and adds its own.

The checks, in the order they print:

### The other report commands

`workloadctl validate <name>` checks the TOML against the schema and against
the host: names, groups, volume paths, secrets (as root), build settings.
Run it after every edit. `workloadctl drift <name>` prints the difference
between the running units and the ones the TOML would produce now, and
exits 1 when there is one. `workloadctl health <name>` is a short liveness
probe that exits 0 or 1, meant for scripts and monitoring. For a
single-container workload it checks that the service is active, the user
exists, the container is running and its health check passes, and each
published port accepts a connection; for a multi-container workload or a VM
it checks less ([Checking health](04-containers.md#checking-health)).

## Starting

### The workload never starts

Check `diagnose` first. A `workload_disabled` line means the workload has no
`.enabled` marker, so nothing starts it at boot; `sudo workloadctl enable
<name>` adds it.

An enabled workload that has no units was skipped by the generator. For a
skip at boot, the **Generator** section of `doctor` shows why; `enable`
prints the same lines to your terminal; and `workloadctl validate <name>`
reports the error with a suggested fix. The usual reasons are a TOML that
fails validation, such as a `[container] systemd` value other than
`"always"`, `"true"` or `"false"`; a `[workload] name` that differs from its
directory's name; and `userns = "host"` without `unsafe_host_userns = true`.

A workload name is at most 27 characters, starts with a lowercase letter
and contains only lowercase letters, digits and hyphens, so that the user
name `_wl-<name>` fits the system's limit. `create` and `init` refuse a
longer name, and `validate` reports one in a directory you made yourself.

### `enable` stops before starting anything

`enable` runs pre-flight checks before it starts anything, and when one
fails it lists what is missing, leaves the workload disabled and exits: a
file named in `[setup] required_files`, an absolute volume path that does
not exist, a group in `extra_groups` the host does not have, an image with
`pull = "never"` that has not been built, or, for a VM, QEMU, its firmware
or `/dev/kvm`. `validate` reports most of these first. Create what is
missing and run `enable` again.

On a bootc host, a group the image defines only in `/usr/lib/group`, such as
`video`, `render` or `input`, is copied into `/etc/group` when the workload
is set up, so the workload user can join it. A group that exists in neither
file has to be created.

### The service fails with status 125, 126 or 127

These are podman's exit codes, not the application's. 125 means podman
itself failed: the image is missing, an option is wrong, a device or volume
does not exist. 126 means the command could not be executed, and 127 that
it was not found in the image. The error podman printed is in `workloadctl
logs <name>`. To see it interactively, run the image by hand as the
workload user:

```bash
sudo workloadctl incant <name> -- run --rm -it <image> /bin/sh
```

`incant` runs podman as the workload user, with the runtime directory, home
and session bus its rootless podman needs. A plain `sudo -u _wl-<name>
podman` lacks them, and fails in ways that have nothing to do with the
workload.

### The container exits as soon as it starts

Any other exit status is the application's own, and its output in `logs`
says why. If there is none, the command probably runs in the background and
returns, as daemons do by default: run it in the foreground, as with
`command = ["nginx", "-g", "daemon off;"]`. An exit status of 1 beside
"Operation not permitted" or "Function not implemented", or 159 beside "Bad
system call", points to [seccomp](#seccomp).

### The unit restarts over and over

`doctor` shows the restart count and the journal of the unit that is
looping. systemd restarts a failed container unit after five seconds, up to
five starts in five minutes, and a VM after ten seconds, up to three. After
that the unit is left down, with "Start request repeated too quickly" in
its status. Once you have found the cause, `sudo workloadctl recreate
<name>` clears that state and starts the workload again.

A unit that sits in `activating` and never becomes active usually has
`service_type = "notify"`, which does not work for container workloads; see
[Service type and timeouts](04-containers.md#service-type-and-timeouts).

### Errors about `pause.pid`, `/run/user/<uid>` or `226/NAMESPACE`

These messages, from a container workload, mean the workload user's runtime
directory `/run/user/<uid>` or its systemd manager `user@<uid>.service` is
gone:

```
Error: ... unable to create a new pause process: open /run/user/10000/libpod/tmp/pause.pid: no such file or directory
Failed to obtain podman configuration: lstat /run/user/10000: no such file or directory
Failed to add pause process to systemd sandbox cgroup: dial unix /run/user/10000/bus: connection refused
```

The unit itself may fail with `226/NAMESPACE`. Rootless podman needs both:
the directory holds its pause process and temporary state, and the manager
provides the bus its cgroup handling talks to. Linger keeps them alive with
nobody logged in, so this happens when linger is off, or when something
removed the session while linger was on. `loginctl terminate-user` does
exactly that, and is the command not to use on a workload user.

`diagnose` reports it as `linger_enabled`, `user_session` or `runtime_dir`
and prints the fix for your case:

```bash
sudo systemctl restart user@<uid>.service     # linger is on: recreates /run/user/<uid>
sudo loginctl enable-linger <uid>             # linger is off: enables it and creates the directory
sudo workloadctl incant <name> -- system migrate   # if podman still complains afterwards
sudo workloadctl restart <name>
```

`podman_session` failing means the same thing seen from the other side: the
workload's podman could not answer, so `diagnose` skipped its image and
container checks.

### Edits to the TOML have no effect

`restart` restarts the units that exist; it does not regenerate them, and
neither does `systemctl daemon-reload`. `diagnose` reports an edit that has
not been applied as `config_current`, and `drift` shows what would change.
Apply it:

```bash
sudo workloadctl validate <name>
sudo workloadctl recreate <name>
```

`recreate` does not validate the file. When the generator rejects the TOML,
the old units stay, and `recreate` restarts the workload on them and
reports success. `edit`'s own apply prompt regenerates the units and
restarts the workload but skips the rest of what `recreate` does; see
[Applying a change](09-operating.md#applying-a-change).

After a package upgrade, running workloads keep the units the previous
version generated until they are recreated or the host reboots. `diagnose`
reports this as `units_current`, and `sudo workloadctl recreate <name>`
regenerates them and restarts the workload. See
[Upgrading](02-installing.md#upgrading).

### Something the setup script installed is failing

A workload whose `[host] setup` script declares what it installs on the host
gets one `host_artifact[...]` check per item: a unit that is missing,
failed or restart-looping, a file that is missing, or a certificate that has
expired or expires within 30 days. `sudo workloadctl enable <name>` runs the
setup script again; `journalctl -u <unit>` shows why a unit is failing; a
certificate's renewal is the bundle's own business, and its README says how.

### Starting over

`disable` without `--purge` stops a workload and keeps its user, its
subordinate ID ranges and everything under `/var/lib/workloads/<name>/`, so
that a later `enable` picks up where it left off. To rebuild a workload from
nothing, remove all of it and enable it again:

```bash
sudo workloadctl disable <name> --purge --dry-run
sudo workloadctl disable <name> --purge
sudo workloadctl enable <name>
```

`--purge` deletes `data/` as well as `state/`, so take a `backup` first if
anything there matters. Users and directories left behind by workloads
whose configuration was deleted by hand are found by `sudo workloadctl
cleanup`; see [Cleaning up](09-operating.md#cleaning-up).

## Images

### "short-name resolution enforced but cannot prompt without a TTY"

The image is named without a registry, such as `nginx:alpine`, and podman
will not guess one without asking. Write the full name, such as
`docker.io/library/nginx:alpine`.

### The image cannot be found or pulled

`diagnose` reports a missing image as `image_available`. An image with
`pull = "never"` is never fetched, so it has to be built:

```bash
sudo workloadctl build <name>
sudo workloadctl recreate <name>
```

For any other image, pull it as the workload user to see podman's whole
error, which names the cause: a misspelt name, a registry that wants a
login, a rate limit, or no route to the registry.

```bash
sudo workloadctl incant <name> -- pull <image>
```

A filtered container cannot pull an image its filter does not allow, and
the refusal looks like a registry outage; see [The image
pull](06-networking.md#the-image-pull).

### "unable to get local issuer certificate" from a private registry

The host does not trust the registry's certificate authority. If its root
is in `/etc/pki/ca-trust/source/anchors/` and the error persists,
`diagnose` reports `ca_trust_anchors`: the anchor is installed but missing
from the extracted bundle that TLS clients read, so it grants no trust. The
fix is `sudo update-ca-trust`. On a bootc host whose anchors all come from
the image, `diagnose` names a better fix: copy the image's extracted bundle
back over the host's, so later anchor changes in the image apply by
themselves. The check runs for container workloads only.

### diagnose says an image is too old

`image_current` fails for an image built more than 30 days ago, so `doctor`
counts it as a problem even though the workload runs. The image's known
vulnerabilities only grow while it sits. `sudo workloadctl update <name>`
pulls a newer one; for an image you build, `build` and then `recreate`.

## Permissions and ID maps

### "newuidmap: write to uid_map failed" or "creating blob layer: permission denied"

The workload user has no subordinate UID or GID range, so podman cannot set
up the container's user namespace or unpack an image. `diagnose` reports
`subid_configured` and prints the fix, which runs the workload's setup step
again:

```bash
grep _wl-<name> /etc/subuid /etc/subgid
sudo /usr/libexec/workloadctl/workload-ensure-user <name>
```

### diagnose reports `subid_derived` or `subid_overlap`

Each workload's subordinate range is derived from its UID: UID 10000 gets
65536 IDs starting at 600100000, and each later UID the next 65536. The
derivation puts every range above the window `useradd` allocates from,
which is what keeps a workload's IDs apart from any human user's.
`subid_derived` fails when the range in `/etc/subuid` or `/etc/subgid` is
not the derived one, and `subid_overlap` when it starts inside `useradd`'s
window as `/etc/login.defs` defines it.

workloadctl never moves an existing range, because shifting the IDs under a
container breaks it. Remapping is a manual job, done with the workload
stopped: write the derived range (the check prints it) into both files, then
shift the ownership of every file under `state/` from the old range to the
new. Leave `data/` alone: its files belong to the workload's own UID, not to
the subordinate range.

UIDs run from 10000 to 52948, so a host can hold 42,949 workloads.

### A volume refuses writes, or its files belong to large UIDs

Under the default user namespace, the container UID equal to the workload's
own UID is the workload user on the host, and every other container UID,
root included, is a subordinate ID. An image that runs as a fixed user, say
UID 1000, therefore writes files the host sees as owned by a large number,
and cannot write to a directory the workload user owns. Make that UID the
workload user, recreate, and give the existing files back to it:

```toml
[security]
userns = "keep-id:uid=1000,gid=1000"
```

```bash
sudo workloadctl recreate <name>
sudo chown -R _wl-<name>:_wl-<name> /var/lib/workloads/<name>/data/<volume>
```

[Who owns the files](04-containers.md#who-owns-the-files) explains the
mapping. Directories under `data/` and `state/` are created for you. An
absolute host path is yours: create it, give it to `_wl-<name>`, and either
mount it with the `Z` option or declare it as a share, so it carries a
label the container may use. A path on cifs, NFS or vfat needs its label
from the mount instead; see [Host paths on other
filesystems](04-containers.md#host-paths-on-other-filesystems).

`volume_paths` in `diagnose` lists host paths that do not exist.
`mcs_labels` lists files under `data/` that are not at the workload's own
SELinux level, which another workload could reach where their modes allow;
`sudo workloadctl recreate <name>` puts them back. Do not use `chcon` or
`restorecon` on a workload's directory: both leave the files at the default
level, which every workload shares.

### Containers with `userns = "host"`

With `userns = "host"`, which needs `unsafe_host_userns = true`, the
container shares the user namespace of the workload's podman. Container UID
0 is the workload user, and container UID N (from 1) is host UID
`subuid_start + N - 1`, where `subuid_start` is the start of the workload's
range. `diagnose` prints the mapping as `uid_mapping`, and `host_userns`
reminds you that the workload runs without its own namespace. Give files to
the host UID the formula yields.

### sshd inside a container refuses keys

sshd refuses an `authorized_keys` file, or a `.ssh` directory, that is not
owned by the login user as the container sees it or that others can write.
Find the host UID that the login user maps to (the workload user, if you set
`userns` to that user's UID), give the files to it, and tighten the modes:

```bash
sudo chown -R _wl-<name>:_wl-<name> /var/lib/workloads/<name>/data/.ssh
sudo chmod 700 /var/lib/workloads/<name>/data/.ssh
sudo chmod 600 /var/lib/workloads/<name>/data/.ssh/authorized_keys
```

### systemd inside a container: "Failed to set up mount namespacing"

systemd as the container's PID 1 must be root in its namespace, which
[Containers that run systemd](04-containers.md#containers-that-run-systemd)
sets up. A service inside the image that asks systemd for sandboxing
(`PrivateTmp=`, `ProtectSystem=` and the like) also needs to mount
filesystems and create namespaces. The seccomp baseline refuses both, and
the container has no `SYS_ADMIN` capability, so the service fails with
"Failed to set up mount namespacing: Permission denied". Turn the
sandboxing off for that service in the image, with a drop-in. Taking the
mount and namespace calls back with `seccomp_allow` and adding `SYS_ADMIN`
to `capabilities` also works, but gives up much of the container's
confinement; see [Capabilities](08-security.md#capabilities) and
[Seccomp](08-security.md#seccomp). "Failed to set RLIMIT_CORE:
Operation not permitted" means the container lacks the `SYS_RESOURCE`
capability.

## Networking and ports

### "address already in use"

Another process already listens on a port the workload publishes, often
another workload. `ss` names the process holding the port, and `info` lists
the ports a workload publishes. Move one of them:

```bash
sudo ss -tlnp | grep ':8080 '
workloadctl info <name>
sudo workloadctl edit <name>
```

### The port answers from other machines but not from the host

Under pasta, the default network, a published port is bound on the host's
network address, not on its loopback, so `curl localhost:<port>` on the
host itself is refused while the workload is healthy. Test against the
host's address.

`workloadctl health` probes each published port from the host itself, where
the port actually answers: a port bound to one address at that address, a
pasta port published on every address at the host's address (the `HOST_IP`
the setup step recorded), and a host-network port at `localhost`.

### Nothing answers from other machines

Check the workload first with `health` or from the host's address. If it
answers there, the host's firewall is refusing the port:
`sudo firewall-cmd --list-all` shows what firewalld allows. A port below
1024 cannot be published by a workload at all until the host's unprivileged
port floor is lowered; see [Ports below
1024](02-installing.md#ports-below-1024).

### Containers cannot find each other

Each workload has a podman of its own, so containers in different workloads
share no network and cannot resolve each other by name. Put containers that
talk to each other in one workload, in `pod` or `bridge` mode; see
[Several containers in one workload](04-containers.md#several-containers-in-one-workload).
A named podman network in `[network] mode` must already exist in the
workload user's podman:

```bash
sudo workloadctl incant <name> -- network create <network>
```

### A filtered workload cannot reach something

Timeouts to ports other than 80 and 443, lost DNS in a bridge-mode
container, and refusals by name all have their own entries in
[Networking](06-networking.md#when-a-request-is-refused).

## VMs

### Every VM fails with "QMP socket not ready after 60s"

The VM's unit fails and restarts until systemd gives up, with this in its
status and no error from QEMU:

```
Status: "Timeout waiting for QMP: QMP socket not ready after 60s: /run/workload-vm/<name>/qmp.sock"
```

A VM with shared directories may fail one step earlier, with a message that
looks like a plain permission problem:

```
virtiofsd: Error creating pid file '/run/workload-vm/<name>/virtiofs-<tag>.sock.pid': Permission denied (os error 13)
workload-<name>.service: A dependency job for workload-<name>.service failed.
```

When every VM on the host fails like this and containers are fine, the
cause is SELinux. QEMU runs confined as `svirt_t`, and `virtiofsd` as
`wlvfsd_t`, and neither may create files in a directory with `/run`'s
default label, so QEMU dies creating its first socket and never opens QMP.
The directory gets its proper label from a file-context rule the package
registers when it is installed. The directory is on a tmpfs and is
recreated at every boot, so a lost rule breaks every VM at the next boot,
not at the moment it was lost. If `dnf install` or `dnf upgrade` ever
printed "workloadctl: WARNING: could not register the SELinux fcontext
rule", act on it then.

`diagnose` reports it as `vm_socket_dir_selinux`. The audit log names the
domain that was refused:

```bash
sudo grep -a denied /var/log/audit/audit.log | grep -aE 'qemu|virtiofsd' | tail
```

A restart does not fix it, because the unit keeps its runtime directory
across restarts, mislabelled or not. Register the rule, then stop the VM,
relabel the directory and start the VM again:

```bash
sudo semanage fcontext -l -C | grep workload
sudo ls -Zd /run/workload-vm /run/workload-vm/<name>
sudo semanage fcontext -a -t svirt_var_run_t '/run/workload-vm(/.*)?'
sudo workloadctl stop <name>
sudo restorecon -R /run/workload-vm
sudo systemctl daemon-reexec
sudo workloadctl start <name>
```

The rule is written with the type `svirt_var_run_t`, and `ls -Z` shows the
same type by its other name, `qemu_var_run_t`. `restorecon` takes no `-F`
here, because the type is not one `restorecon` leaves alone.
`daemon-reexec` is needed because systemd loads the file-context rules when
it starts and labels the runtime directories it creates from that copy, so
until it re-executes it keeps creating the directory with the old label.

### diagnose reports `selinux_labels` or `vm_confinement` for a VM

A VM's directory under `/var/lib/workloads/` must be labelled
`svirt_image_t`, which a rule registered for each VM at `enable` provides.
A host rebuild can lose it, and then the confined QEMU is refused its own
disks. `sudo workloadctl recreate <name>` registers the
rule again and relabels the directory.

`vm_confinement` fails in two cases. QEMU is running as a type other than
`svirt_t`, so the VM is not confined: check that `/usr/bin/runcon` exists,
then restart the VM. Or the `workload-vm` policy module is not loaded, so a
confined QEMU cannot reach its `virtiofsd` sockets and the VM's shared
directories do not mount. Load it, and relabel the program it confines:

```bash
sudo semodule -i /usr/share/workloadctl/workload-vm.cil
sudo restorecon /usr/libexec/virtiofsd
```

### `shell` and `exec` cannot get in

On a first boot, cloud-init may not have created the login user or
installed the key yet: wait for it, or watch the boot on the serial console,
which works whatever state SSH is in:

```bash
sudo workloadctl shell <name> --console
```

`shell` falls back to the console by itself when SSH cannot connect at all.
A VM that boots, reports `active` and logs in on the console, but refuses
SSH, usually has a shared directory mounted over the login user's home; see
[What breaks a share](05-vms.md#what-breaks-a-share).

### diagnose reports `vm_provisioning`

cloud-init failed inside the guest, and the guest is only partly set up:
users, sudo rules or `runcmd` steps may be missing, and cloud-init does not
try again by itself. `diagnose` prints the first error the guest recorded.
Fix its cause, usually in the seed, then run `sudo workloadctl recreate
<name>`. The guest gets a new instance ID when the seed has changed, and
once more after a recorded failure even when it has not, so cloud-init runs
its per-instance modules again on the next boot. If it fails again with the
seed unchanged, workloadctl does not retry. A cattle VM can then be rebuilt
from its image with `sudo workloadctl update <name>`, which keeps `data/`
and shared directories; on a pet, log in on the console and repair it by
hand.

### diagnose reports `vm_guest_clock`

The line fails in two ways. "guest agent does not answer" means the guest
does not run `qemu-guest-agent`, so the host's clock keeper cannot see or
set its clock, and after a pause the guest stays behind; install and enable
the agent in the guest. A clock more than five minutes out means the keeper
has not corrected it, which it should do within a minute of a resume; check
`systemctl status workload-<name>-clock.timer`. [The guest's
clock](05-vms.md#the-guests-clock) covers the guest-side remedy.

### The data disk never appeared

The data disk is created when the system disk is built. Adding
`data_disk_size` to a VM that already has a system disk creates nothing
until a cattle VM's next `update`; see [The data disk](05-vms.md#the-data-disk).

### The guest cannot reach a service on its own host

Inside the guest, the host's main address is the guest's own address, and
the host's loopback is not mapped in. [The guest's
network](05-vms.md#the-guests-network) describes the one address a VM can
reach its host on.

## Virtiofs shares

[What breaks a share](05-vms.md#what-breaks-a-share) lists the common
symptoms of a share that does not work. These are the less common ones.

### The pid file's "Permission denied" survives a restart

The sidecar removes a stale pid file at every start, so an `Error creating
pid file … Permission denied` that persists comes from the runtime
directory's label; see [Every VM
fails](#every-vm-fails-with-qmp-socket-not-ready-after-60s).

### `ln -s` or `df` fails with EPERM while reads and writes work

The `workload-vm` module the host has loaded lacks a permission. `diagnose`
reports a module older than the package's as `selinux_module_current`, with
the `semodule -i` command that loads the current one. If the module is
current, the audit log names the missing permission, and the package's
policy is at fault.

### A `dac_read_search` denial at every start

One `dac_read_search` denial for `wlvfsd_t` each time the sidecar starts,
with the share working, means something has changed the sidecar's command
line. The generated unit runs `virtiofsd` with `--inode-file-handles=never`,
which avoids the call; look for a drop-in under
`/etc/systemd/system/workload-<name>-virtiofs-<tag>.service.d/`.

### A sidecar started by hand works where the unit fails

Started by hand, or under `strace`, `virtiofsd` does not enter its SELinux
domain and runs unconfined, so the denial that stops the unit never
happens. Reproduce through systemd instead, for example with
`systemd-run`.

## SELinux denials

### Finding the denial

A denial is recorded in the audit log, whatever the program printed:

```bash
sudo ausearch -m AVC,USER_AVC,SELINUX_ERR -ts recent
sudo grep -a denied /var/log/audit/audit.log | tail -20
```

The `scontext` of each record says which process was refused:

| Type | Process |
|---|---|
| `container_t` | a container, by default |
| `wl_<name>.process` | a container of a workload with `selinux_policy = true`, its name's hyphens written as underscores |
| `svirt_t` | a VM's QEMU |
| `wlvfsd_t` | a VM's `virtiofsd` sidecar |
| `wlinspect_t` | a filtered workload's egress inspector |
| `wlresolve_t` | a filtered workload's DNS responder |
| `wlclock_t` | a VM's clock keeper |

Some denials are not logged, because the policy marks them as expected
noise. A container that gets "Permission denied" with no record in the log
may be meeting one of those. Turn the hidden records on while you
reproduce, and off again afterwards:

```bash
sudo semodule -DB
sudo semodule -B
```

Programs often report a denial as something else: a file that "does not
exist", a timeout, an exit status `203/EXEC`. When a confined process fails
for no visible reason, read the audit log before anything else.

### Labels

workloadctl labels the trees it manages itself. A container workload's
directory is `container_file_t` and a VM's `svirt_image_t`, each at the
workload's own SELinux level, and `diagnose` checks both the label and the
rule behind it (`selinux_labels`, `mcs_labels`). The fix it prints is
`sudo workloadctl recreate <name>`, which relabels the tree and sets the
level in one pass, preceded for a container workload by a `semanage` command
when the rule itself is missing. `restorecon` would reset the level to the
one every workload shares.

For a path outside those trees, register a rule and relabel. `restorecon`
needs `-F` for `container_file_t` and `svirt_image_t`, which it otherwise
leaves alone:

```bash
sudo semanage fcontext -a -t svirt_image_t '/srv/media(/.*)?'
sudo restorecon -RF /srv/media
```

A `filecon` line in a workload's `policy.cil` for a path under
`/var/lib/workloads` or `/run/workload-vm` has no effect, because the rules
workloadctl registers outrank it; `validate` warns about one. On a
filesystem that cannot store labels, `semanage` and `restorecon` appear to
succeed and change nothing: the label comes from a mount option (see [Host
paths on other filesystems](04-containers.md#host-paths-on-other-filesystems)).

### Policy modules

`selinux_module` fails when a workload with `selinux_policy = true` has no
module loaded, and `workload_selinux_module_current` when the loaded module
grants less than the workload's `policy.cil` asks for. `sudo workloadctl
enable <name>` loads the current one.

`selinux_module_current` covers the package's own modules: `workload-vm`,
`workload-inspect`, `workload-resolve` and `workload-clock`. It fails when
the policy in force does not grant what the installed module asks for, and
names the `semodule -i` command for each. On a bootc host whose policy
store is in `/etc`, this is the expected state after an image upgrade; see
[Policy modules on bootc hosts](08-security.md#policy-modules-on-bootc-hosts).

### Devices

`gpu_selinux` fails when a workload asks for an NVIDIA GPU and nothing
grants access to `/dev/nvidia*`. Its fix is a boolean:

```bash
sudo setsebool -P container_use_xserver_devices on
```

A workload with its own policy module must grant the access in its
`policy.cil`, because the boolean covers only the default container type.
On a host that still has the older `container_use_devices` boolean on, which
gives every container every device node type, the check passes with a
warning. Its fix turns the scoped boolean on and leaves the older one alone:
other workloads, such as jellyfin transcoding on a `/dev/dri` render node,
open their devices through it. Turn it off only when nothing on the host
does.
For other devices, the denial in the audit log names the device's type, and
a workload's own `policy.cil` is the place to allow it; see [A policy of the
workload's own](08-security.md#a-policy-of-the-workloads-own).

## seccomp

Every container runs under a seccomp profile that refuses a set of system
calls most software never makes. [Seccomp](08-security.md#seccomp) lists
what it refuses and why; this section is about recognising a refusal and
undoing it for one workload.

### What a refused call looks like

The application, not podman, fails, so the exit status is its own (often
1) and the message names an operation:

```
ptrace: Function not implemented
bpf: Operation not permitted
bwrap: No permissions to create a new namespace
```

A 32-bit program dies at its first system call with "Bad system call (core
dumped)" and exit status 159. A call the profile does not name fails with
"Function not implemented", as if the kernel lacked it; one it refuses by
name fails with "Operation not permitted". An "Operation not permitted"
from a call the profile allows comes from somewhere else: a missing
capability, or SELinux.

Calls the profile logs or kills leave an audit record:

```bash
sudo journalctl _AUDIT_TYPE=1326 --since -1h
```

To confirm, run the image once without the profile, as the workload user,
and see whether the failure goes away:

```bash
sudo workloadctl incant <name> -- run --rm --security-opt seccomp=unconfined <image>
```

### Taking calls back

Open only what the workload needs, in the top-level `[security]`; the rest
of the profile still applies. [Opening it for one
workload](08-security.md#opening-it-for-one-workload) has each key's
examples and limits.

| What fails | Key |
|---|---|
| a debugger: `ptrace: Function not implemented` | `seccomp_allow = ["ptrace", "process_vm_readv", "process_vm_writev"]` |
| bubblewrap, as in Steam's runtime and Flatpak: `No permissions to create a new namespace` | `seccomp_allow = ["clone", "mount", "pivot_root", "umount2", "unshare"]` |
| `wg` and `wg-quick`, over generic netlink | `seccomp_netlink = ["generic"]` |
| `ss`, over sock_diag | `seccomp_netlink = ["sock_diag"]` |
| a 32-bit program: a `SECCOMP` audit record with `arch=40000003` | `seccomp_32bit = true` |

WireGuard needs one more thing: a container cannot load the module either,
which `wg-quick` reports as "Unknown device type", so add
`kernel_modules = ["wireguard"]` beside `seccomp_netlink`.

A `seccomp=` entry in `security_opt` replaces the profile instead of adding
to it. Prefer the keys above. Apply any of these with
`sudo workloadctl recreate <name>`; a pet container keeps the profile it was
created with until it is recreated.

## Egress refusals

[When a request is refused](06-networking.md#when-a-request-is-refused) is
the place to start for a filtered workload whose requests fail: it maps
each symptom to a cause, and `sudo workloadctl egress <name> --decision
drop` shows what the inspector refused and why. Three failures it does not
cover follow.

### Web requests hang after you filter a running container

Every request to ports 80 and 443 hangs after you add `hosts`, or another
filter trigger, to a running container and answer `y` at `edit`'s prompt.
The prompt regenerates the units and restarts the container, and the
container's unit arms the redirect to the inspector. The inspector's
certificate authority and state are created by the workload's setup step,
which the prompt does not run, so nothing answers behind the redirect. Run
`sudo workloadctl recreate <name>`, which runs the setup step. A plain
`restart` applies nothing at all, and the container stays unfiltered until
you recreate it.

### The inspector says its CA "is not there"

The inspector will not start, saying the workload's egress CA "is not
there", and the file exists. A lookup SELinux refused reads as a missing
file. Check the audit log for `wlinspect_t` denials and the labels of the
workload's three PKI directories:

```bash
sudo ls -Zd /var/lib/workloadctl/egress/<name>/{ca,leaves,leaves-denied}
```

`ca` should be `wlinspect_ca_t` and the other two `wlinspect_leaf_t`, at
the workload's level. `sudo workloadctl recreate <name>` relabels them.

### diagnose says the filter is not in force

`diagnose` names the missing piece (the default deny, the redirect, the
listener, a policy older than the TOML) and the unit to restart. After a
[break-glass](06-networking.md#break-glass) deletion, every filtered
workload reports this until it is restarted.

## Secrets

### A secret does not reach the container

Work from the store towards the container. First, as root, `validate`
checks that every secret the TOML references exists:

```bash
sudo workloadctl validate <name>
sudo workloadctl secret show <secret>
```

`secret show` proves the secret decrypts on this host. One sealed to a TPM
that has since been cleared, or on another machine, does not, and a unit
that loads it fails to start with status `243/CREDENTIALS`.

Next, check that the running unit loads it. A reference added after the
units were generated is not loaded until `recreate` regenerates them:

```bash
systemctl cat workload-<name>.service | grep LoadCredentialEncrypted
sudo ls /run/credentials/workload-<name>.service/
```

In a multi-container workload each container has a unit of its own,
`workload-<name>-<container>.service`, which loads only the secrets that
container references. A top-level `[secrets]` section is ignored there:
each container needs its own `[containers.secrets]`.

A secret with a newline in its value cannot become an environment
variable. The workload fails to start with "Secret value for KEY contains
newlines; use secrets.files[] instead of env var injection". Mount it as a
file, or seal it again without the newline (`printf '%s'`, not `echo`).

Last, look inside the container:

```bash
sudo workloadctl exec <name> printenv API_KEY
sudo workloadctl exec <name> ls -l /etc/webapp/tls/
```

A pet container keeps the environment it was created with, so after a
rotation `restart` does not give it the new value; `recreate` does.

### A secret does not reach a VM

A VM's secrets go into its cloud-init seed when the seed is built. If a
`${SECRET:name}` placeholder names a secret that does not exist, the seed is
not built and the VM does not start; `${SECRET?name}` gives an empty value
instead. A rotated secret reaches the guest only when the seed is built
again, with `sudo workloadctl recreate <name>`. [Giving a secret to a
VM](07-secrets.md#giving-a-secret-to-a-vm) covers the rest.

Broker credentials are checked differently, since the workload never holds
them; see [Credentials for the broker](07-secrets.md#credentials-for-the-broker)
and [Networking](06-networking.md#when-a-request-is-refused).
