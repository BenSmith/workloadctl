# 9. Operating

This chapter covers the day-to-day work on workloads that already exist:
starting and stopping them, applying edits, ordering them at boot, updating
and rolling back their images, backing them up, reading their logs and
metrics, and cleaning up after them. VM disks, generations and the guest's
own logs are in [VM workloads](05-vms.md), and diagnosing a failure in depth
is in [Troubleshooting](10-troubleshooting.md).

Every command that changes a workload needs `sudo`. These commands also take
`-q`, which drops the progress narration but keeps warnings and errors, and
`--json`, which prints a result document instead of the narration.
[Reference](11-reference.md) describes that document.

## Seeing what is there

```bash
workloadctl list
workloadctl status web
```

`list` shows every workload under `/etc/workloads.d/`, enabled or not, with
its state, image and ports. `status <name>` runs `systemctl status` on the
workload's units. Above that output it warns when the TOML has been edited
since the units were generated, and when the units were generated by a
different build of workloadctl. `status --json` reports the same facts as
JSON.

## Enabling and disabling

```bash
sudo workloadctl enable web
sudo workloadctl disable web
sudo workloadctl disable web --purge --dry-run
```

`enable` brings a workload up from its TOML, one step at a time. It marks the
workload enabled and checks its prerequisites. Then it runs its host setup
script, loads any SELinux policy module it declares and generates its units.
It creates its user and directories, copies an image built on the host into
the workload's own store, and starts it. It does not wait for the workload to
come up, because a first image pull can take minutes, so follow it with
`status` and `logs`.

If a prerequisite is missing, `enable` names it and leaves the workload
disabled. The missing thing can be a tool, a required file or an absolute
volume path ([Files the workload needs first](04-containers.md#files-the-workload-needs-first)).
By then it has already created the workload's directories under
`/var/lib/workloads/<name>/`, so you can copy files into place and run
`enable` again.

`enable` is safe to repeat. On a workload that is already running, it
regenerates the units and starts nothing, so the workload keeps running on
its old configuration until its next restart. To apply an edit, use
`recreate` ([Applying a change](#applying-a-change)).

`disable` stops the workload and its helper units, and runs its host setup
script's teardown. It removes its SELinux policy module and its generated
units, and deletes the enabled marker. It keeps the workload's user, its
subordinate ID ranges and everything under `/var/lib/workloads/<name>/`, so a
later `enable` picks up where it left off.

`disable --purge` deletes more:

- the user and its ID ranges;
- all of `/var/lib/workloads/<name>/`, data included;
- the workload's egress CA and its per-request egress record;
- its runtime files.

It leaves `/etc/workloads.d/<name>/` and the host's secrets alone. `--dry-run`
prints exactly what either form would stop and delete, including the size of
the data directory, and changes nothing. Archives made by `backup` are kept
outside the workload's directory and survive a purge, so take one first.

`disable` is best effort. A step that fails does not stop the ones after it.
The command reports every failure at the end and exits 1.

### The enabled marker

Whether a workload is enabled comes down to one file,
`/etc/workloads.d/<name>/.enabled`. At every boot, workloadctl generates
units for each workload that has one, and starts it. A workload without the
marker is left alone.

You can create or delete the marker yourself, as a bootc image does
([Installing](02-installing.md#in-a-bootc-image)). The change takes effect at
the next boot. On a running host, use `enable` and `disable` instead.
`systemctl daemon-reload` does not generate a workload's units, so after you
create the marker by hand, `systemctl start` finds no unit to start.

## Starting, stopping and restarting

```bash
sudo workloadctl stop web
sudo workloadctl start web
sudo workloadctl restart web
```

`start` and `stop` do not change whether the workload starts at boot. A
stopped workload that is still enabled starts again at the next boot.

`restart` stops and starts the workload's units as they are. It does not
regenerate them, so it does not apply an edit to the TOML. What survives
depends on the workload's lifecycle:

- a `cattle` container is created afresh from its image, and its writable
  layer is lost, as it is at every stop;
- a `pet` container is stopped and started again, writable layer and all;
- a VM is power-cycled onto the same disks and the same cloud-init seed.

When a container exits with an error, systemd restarts it five seconds
later. After five starts in five minutes it gives up and leaves the unit
failed. `start`, `restart` and `recreate` clear that state. VMs have limits
of their own ([Running the VM](05-vms.md#running-the-vm)).

`reboot` soft-reboots the workload's own systemd. That works for a container
that runs systemd as its init (`[container] systemd`), and for a VM, where
the command goes over SSH. The container or the disk is kept, and everything
inside restarts. The workload needs systemd 254 or later inside it.

## Applying a change

```bash
sudo workloadctl validate web
sudo workloadctl recreate web
```

`recreate` is how an edited TOML reaches a running workload. It does all of
the following:

- regenerates the workload's units and clears any failed state;
- updates its SELinux file contexts and its share membership;
- reruns its setup step, which creates whatever the new configuration needs
  on the host, such as directories or an egress CA;
- copies an image built on the host into the workload's store;
- restarts the workload on the new units.

A cattle container is created afresh. A pet container's writable layer is
saved first ([Pet snapshots](#pet-snapshots)), and then the container is
replaced. A VM gets a new cloud-init seed rendered from the current TOML and
is power-cycled, and its disks are kept.

`recreate` does not validate the file. If the generator rejects the TOML, it
leaves the old units in place, and `recreate` restarts the workload on them
and reports success. Run `validate` before `recreate`.

`workloadctl edit` validates when you save and offers to apply the change. If
the new file is invalid it asks whether to put the old one back; the default
answer keeps your edit, and `edit` exits 1 without applying it. Its apply step
regenerates the units and restarts the workload, but skips everything else
`recreate` does. For a pet container, or for a change that adds an egress
filter, a credential or a share, answer `n` and run `recreate` instead.

| Command | Units regenerated | Cattle container | Pet container | VM |
|---|---|---|---|---|
| `restart` | no | new container from its image | same container | power-cycled, same seed |
| `recreate` | yes | new container from its image | snapshot, then a new container | new seed, power-cycled |
| `update` | no | new container on the newly pulled image | snapshot, then a new container on the new image | system disk rebuilt (cattle) or restarted (pet) |
| `reboot` | no | systemd inside soft-reboots | systemd inside soft-reboots | the guest soft-reboots |

`workloadctl drift` shows when the running units no longer match the TOML
([Drift](#drift)).

## Ordering workloads

Two keys in `[workload]` tie one workload's start to others':

```toml
[workload]
name = "app"
requires = ["db"]
after = ["db", "cache"]

[container]
image = "registry.example.com/app:1.4"

[network]
ports = ["8080:8080"]
```

`after` sets an order. When `app` and `db` start at the same time, `app`
waits until `db` has started. It creates no dependency, so starting `app` on
its own does not start `db`. `requires` creates a dependency: starting `app`
starts `db` too. Despite its name, `requires` does not fail `app` when `db`
fails, and it sets no order between them. For "start `db` first", list the
name in both keys, as above. In systemd's terms, `requires` becomes `Wants=`
and `after` becomes `After=` on the workload's unit.

"Started" means what systemd means by it. It does not mean that the service
inside is ready. A container counts as started once podman is running, and
a VM once its virtual CPUs are. If `app` fails when `db` is not yet
accepting connections, the restart policy above starts `app` again five
seconds later. For anything slower, make `app` retry on its own.

Neither key stops or restarts anything. Stopping or restarting `db` leaves
`app` running. At boot, every enabled workload is started in one batch, and
this is where `after` matters most.

Each name must be a valid workload name. `validate` warns about a name that
matches no workload on the host. A dependency that is not enabled is
ignored. Both keys work for container workloads only, and every container
in a multi-container workload carries them. In a VM's TOML, `validate`
accepts them, but they are silently ignored. A container workload can still
name a VM in either list.

## Updating container images

```bash
sudo workloadctl update web --dry-run
sudo workloadctl update web
sudo workloadctl update --all
```

`update` pulls the image each container names, whatever that container's
`pull` setting says, unless it is `"never"`. It restarts the workload only if
an image changed. Before the restart, it tags the image each container was
running as `localhost/workload-rollback/<name>:latest` in the workload's own
store. In a multi-container workload, the tag is
`localhost/workload-rollback/<name>-<container>:latest` for each container.
`--force` restarts the workload even when nothing changed.

`--dry-run` contacts no registry. It prints the images `update` would pull,
the image ID each would roll back to, and what it would restart.

After the restart, `update` checks that the workload came back up:

- a workload with health checks gets its longest `start_period` plus
  `interval`, and then every checked container must report healthy. A
  container still starting gets one more `interval`
  ([Health checks](04-containers.md#health-checks));
- a workload without health checks must still be active after five seconds.

A workload that fails the check is put back on its previous images and
restarted. `update` treats that as a handled outcome: it exits 0 and reports
the workload as `rolled-back`. A failed pull, or a restart that does not come
back, makes it exit 1. If a container had no previous image in the store,
`update` warns and leaves that container as it is.

`--all` updates every enabled workload. It pulls and restarts each one, then
checks them all after one shared wait. It skips any workload whose images
are all `pull = "never"`, and one workload's failure does not stop the
others. `--all` includes VMs: a cattle VM's system disk is rebuilt, with no
check afterwards ([Update and rollback](05-vms.md#update-and-rollback)).
Keep that in mind before you put `update --all` on a timer.

`update` keeps the image tag that the TOML names, and it does not regenerate
the units. To move a workload to a new tag or digest, edit `image` and run
`recreate`. The old image keeps its own tag in the store, so going back is
the reverse edit.

`update` refuses a workload whose images are all `pull = "never"`. Rebuild
it with `build` and apply it with `recreate`
([Building your own image](04-containers.md#building-your-own-image)). A
workload that was stopped is started by `update` when its image changes.

## Rolling back

```bash
sudo workloadctl rollback web --list
sudo workloadctl rollback web
```

`rollback` gives each container's saved image the name the TOML uses, then
restarts the workload. It does not check health afterwards. Only one earlier
image is kept per container, because each `update` moves the rollback tag to
the image it replaced.

A rollback is not a pin. The TOML still names the same tag, so the next
`update` pulls the registry's image again. A container with
`pull = "always"` or `"newer"` pulls it again at its next start. To stay on
the old image, either hold off `update` until the registry has a fixed
image, or pin the image in the TOML by version or digest and run `recreate`.
To roll forward, run `update`.

A pet container keeps running from the container it already has. `rollback`
and the automatic rollback inside `update` retag the image, but the
container that restarts is still the one created from the new image. Run
`recreate` after either one to rebuild the container from the old image.
`recreate` saves another snapshot first.

The image you rolled away from loses its name. Images with no name pile up
in each workload's store until you prune them:

```bash
sudo workloadctl images
sudo workloadctl images prune
```

`images` lists the image each workload's containers use. `images prune`
removes every image that no tag refers to, in every workload's store. The
rollback images and pet snapshots carry tags, so pruning keeps them.

VMs roll back between system disk generations instead
([Update and rollback](05-vms.md#update-and-rollback)).

## Pet snapshots

`update` and `recreate` replace a pet container. Before they do, they commit
its writable layer to an image,
`localhost/workload-snapshot/<name>:<timestamp>`, in the workload's own
store. The timestamp is in UTC. After each new snapshot, older ones are
deleted until `snapshot_keep` remain (3 by default):

```toml
[workload]
name = "desktop"
lifecycle = "pet"
snapshot_keep = 5

[container]
image = "registry.example.com/desktop:latest"
```

Only a single-container pet takes snapshots, because a multi-container
workload always runs as cattle. Only `update` and `recreate` take a snapshot:
`restart` and `stop` keep the container. If the commit fails, the container is
replaced anyway, and the warning in the command's output is the only record.
The snapshots live in the workload's `state/`, so `backup` leaves them out and
`disable --purge` deletes them.

To go back to a snapshot, give it the image name the TOML uses and recreate
the container from it:

```bash
sudo workloadctl incant desktop -- images localhost/workload-snapshot/desktop
sudo workloadctl incant desktop -- tag \
    localhost/workload-snapshot/desktop:20261028T101500Z \
    registry.example.com/desktop:latest
sudo workloadctl recreate desktop
```

This works with the default `pull = "missing"`. The next `update` pulls the
registry's image over that tag again.

## Backup and restore

```bash
sudo workloadctl backup web
sudo workloadctl backup web --output /mnt/backup/
sudo workloadctl backup --all --output /mnt/backup/
```

### What a backup holds

A backup is a zstd-compressed tar archive with three parts:

- `workload.toml`, the workload's configuration;
- `credentials/`, the sealed files of the secrets the TOML references. They
  stay sealed, and [Secrets](07-secrets.md#backup-and-restore) explains
  which secrets this leaves out;
- `data/`, a copy of `/var/lib/workloads/<name>/data/`.

From `/etc/workloads.d/<name>/` only the TOML goes in. A `Containerfile`, a
setup script, a `policy.cil`, a VM's cloud-init seed or any other control
file you keep beside the TOML is not in the archive, so copy that directory
too.

`state/` is not in the archive either: the image store, the container
layers, the pet snapshots, and a VM's system disk and its generations.
`enable` rebuilds it from the TOML and the images. The operations log and
the enabled marker stay behind as well.

By default, the archive goes to
`/var/lib/workloads/backups/<name>-<YYYYMMDD-HHMMSS>.tar.zst`. `--output`
(`-o`) names a file or a directory. Archives are readable only by root.
`--all` backs up every workload under `/etc/workloads.d/`, enabled or not,
one archive each, and with it `--output` must be a directory. One failed
workload does not stop the others, and the command exits 1 at the end.
`--json` reports the archives and their sizes.

`backup` stops at mount points. Anything mounted inside `data/` (a network
share, a second disk, a bind mount) is skipped, with a warning that names
each path. Whatever owns the mount should back it up. A `data/` that is
itself a mount, such as a disk of its own, is captured in full.

### Consistency

`--consistency` chooses between stopping the workload for the copy and
copying it while it runs:

- `cold`, the default, stops the workload, copies `data/` and starts the
  workload again. A workload that was already stopped stays stopped. The
  workload is down for the whole copy, and a VM gets up to 80 seconds to
  power off first.
- `crash` does not stop the workload. A container's `data/` is copied while
  the container writes to it, so a file in the middle of a write can be
  captured half-written. Use this only for data that is idle, or that its
  application can recover after a power cut. A VM's virtual CPUs are paused
  through QEMU's monitor for the whole copy and resumed afterwards. The data
  disk is therefore captured as it would be after a power cut. If the guest
  runs `qemu-guest-agent`, its clock is set right after the pause. A VM that
  is not running is copied cold. If the monitor cannot be reached, the
  backup fails rather than copy a disk that is in use.

### Restoring

```bash
sudo workloadctl restore /var/lib/workloads/backups/web-20261028-031500.tar.zst
sudo workloadctl validate web
sudo workloadctl enable web
```

`restore` reads the workload's name from the TOML in the archive, and
restores under that name only. If `/etc/workloads.d/<name>/` already
exists, it refuses unless you pass `--force`. It stops the workload if it is
running. Then it writes the TOML and the sealed secrets, skipping any secret
that already exists unless you pass `--force`, and writes `data/`. If
`data/` already exists, `restore` merges into it: files from the archive
overwrite their namesakes, and other files stay. With `--force`, it
replaces `data/` completely.

`--enable` runs `enable` once the restore finishes. Without it, the workload
stays stopped, even one that was running before a `--force` restore. Its
images are not in the archive, so `enable` pulls them. A VM gets a new
system disk built from its image, so a pet VM comes back as a fresh install
with its data disk.

`restore` refuses to start when it would write somewhere it should not:

- when anything is mounted under `data/`. Without `--force`, the merge would
  write through the mount. With `--force`, deleting the old `data/` would
  delete what is on the other side of the mount, which for a bind mount is
  the original directory. Unmount it first.
- when `data/` is itself a mount and you pass `--force`. Replacing it would
  empty the mounted filesystem. A restore without `--force` merges into the
  mount, which is what a disk mounted there is for.
- when, without `--force`, the existing `data/` has a symbolic link at a path
  the archive writes, because the merge would write through it. With
  `--force`, the tree is replaced and the link is deleted, not followed.
- when the archive holds a symbolic link that points outside `data/`.

`restore` writes everything under `data/` as root, and does not carry over
the file ownership recorded in the archive. When the workload starts, its
user gets back `data/` and the top directory of each `./` volume, but not
the files inside them. A VM's data disk stays root's. Check the ownership
under `/var/lib/workloads/<name>/data/` before you rely on a restored
workload.

### Restoring on another host

A sealed secret opens only on the host that sealed it, so the secrets that
`restore` puts back cannot be read on a new host. Restore without
`--enable`. Import each secret over the restored copy, then validate and
enable:

```bash
sudo workloadctl restore /mnt/backup/web-20261028-031500.tar.zst
sudo workloadctl secret import web-api-key /mnt/backup/web-api-key.secret --force
sudo workloadctl validate web
sudo workloadctl enable web
```

`validate` names any secret the TOML references that is still missing.
[Secrets](07-secrets.md#backup-and-restore) covers exporting the secrets on
the old host, and the secrets a VM's seed references, which `validate`
cannot see.

## Logs

```bash
workloadctl logs web
workloadctl logs -f web
workloadctl logs -n 200 --since "1 hour ago" web
workloadctl logs blog/db
workloadctl logs web -p err -b
```

`logs` shows the last 50 lines unless you ask for something else. `-f`
follows, `-n` sets the number of lines and `--since` starts at a time.
Everything after the workload's name is passed to `journalctl` as it is, so
any `journalctl` option works there. For a multi-container workload, `logs`
merges every container's output in time order, and `<workload>/<container>`
narrows it to one.

Containers use podman's passthrough log driver. A container's output goes
straight into the systemd journal, once, and podman keeps no copy, so
`podman logs` fails with `this container is not logging output`. The journal
files that output under the workload user's own systemd manager, not under
the workload's unit. As a result, `journalctl -u workload-web.service` shows
only the unit's start and stop lines and podman's own messages. `workloadctl
logs` selects by the unit, by the container's log identifier and by the
workload's UID, so it gets all of them.

To use `journalctl` directly, select a container by its identifier. That is
`workload-<name>` for a single container and `workload-<name>-<container>`
for one container of several:

```bash
journalctl -t workload-web
journalctl -f -t workload-blog-db
```

A bundle that runs systemd inside its container forwards that systemd's
journal to the host, under the identifiers its services use inside, such as
`sshd`. `-t workload-<name>` does not match those entries, but the
workload's UID does:

```bash
journalctl _UID=$(id -u _wl-desktop)
```

The journal sets `_UID` itself, so a workload can choose the identifier it
logs under, but not its UID. `workloadctl logs <name>` includes these
entries. The `<workload>/<container>` form does not, because the UID covers
the whole workload.

For a VM, `logs` shows the journal of the VM's unit, which holds QEMU's
messages and workloadctl's. The guest's own journal is inside the guest
([Running the VM](05-vms.md#running-the-vm)). A filtered workload's requests
are recorded separately, and `workloadctl egress` reads them
([Reading a filter](06-networking.md#reading-a-filter)).

## Resource usage

```bash
sudo workloadctl stats
sudo workloadctl stats web
sudo workloadctl stats -f web
sudo workloadctl stats --json
```

Without a name, `stats` covers every enabled workload that is running. `-f`
keeps updating, for one workload. Without a name it follows only the first
workload, and it does not work with `--json`. For a container, the figures
are podman's ([Watching usage](04-containers.md#watching-usage)). For a VM,
they come from QEMU's read-only monitor. CPU is the virtual CPUs' time over
half a second, and memory is what the balloon leaves the guest, against
`[vm] memory`. A VM has no network or disk figures, and `--json` reports
them as `null`, not as zero. `-f` does not work for a VM.

## Metrics

workloadctl ships an exporter that writes Prometheus metrics into text files
for a collector to read. It opens no network port. Two timers run it, and
both are enabled when the package is installed:

| Timer | Runs | Writes |
|---|---|---|
| `workload-exporter.timer` | every 30 seconds, first one minute after boot | `/run/workload-exporter/workloads.prom` |
| `workload-exporter-disk.timer` | every 15 minutes, first three minutes after boot | `/run/workload-exporter/workloads-disk.prom` |

Disk usage has a timer of its own because measuring a large workload
directory can take a while. Both files are replaced in one step, so a reader
never sees half a file. Both are readable by every user. Point
node_exporter's textfile collector at the directory:

```bash
node_exporter --collector.textfile.directory=/run/workload-exporter
```

Any agent that reads the same text format will do. An agent that runs in a
container needs the directory bind-mounted, read-only. `systemctl
list-timers 'workload-exporter*'` shows when the timers last ran.

Every series below carries a `workload` label, except
`workload_enabled_total` and the two timestamps:

| Series | Type | Meaning |
|---|---|---|
| `workload_active` | gauge | 1 while `workload-<name>.service` is active |
| `workload_failed` | gauge | 1 while it is failed |
| `workload_restarts_total` | counter | how many times systemd has restarted it |
| `workload_uptime_seconds` | gauge | time since it became active, while active |
| `workload_cpu_usage_seconds_total` | counter | CPU time used |
| `workload_memory_current_bytes` | gauge | memory in use |
| `workload_memory_max_bytes` | gauge | the memory limit, when there is one |
| `workload_pids_current` | gauge | processes and threads |
| `workload_health` | gauge | 1 healthy, 0 not, for each container with a health check |
| `workload_vm_balloon_actual_bytes` | gauge | a VM's memory after the balloon |
| `workload_vm_vcpu_cpu_seconds_total` | counter | CPU time for each virtual CPU, labelled `vcpu` |
| `workload_disk_bytes` | gauge | the size of `/var/lib/workloads/<name>/`, all of it |
| `workload_enabled_total` | gauge | the number of enabled workloads |
| `workload_metrics_last_collect_timestamp_seconds` | gauge | when the fast file was written |
| `workload_disk_last_collect_timestamp_seconds` | gauge | when the disk file was written |

For a VM, the CPU, memory and process figures come from QEMU's unit. For a
container, they come from the container's own cgroup. In a multi-container
workload they cover one of its containers only, so use `stats` for the
others. `workload_health` carries a `container` label in a multi-container
workload. A workload without health checks has no `workload_health` series.

A filtered workload also gets its egress inspector's counters. These are
the same figures `doctor` prints. Their names begin `workload_vm_inspect_`
or `workload_vm_resolve_`, for containers as well as VMs. They include
connections spliced, terminated, forwarded and dropped, drop events by
`reason`, and requests sent through the credential broker. They also
include, where the workload terminates TLS, certificates minted, and, where
it has its own DNS responder, names answered.
`workload_vm_inspect_status_present` is 0 until the inspector has handled a
connection since it started. An unfiltered workload has none of these
series, and a feature that is off, such as minting under `tls = "splice"`,
has none of its own.

Five expressions are worth an alert:

- `increase(workload_restarts_total[15m]) > 0` catches a workload that keeps
  restarting while it still looks active;
- `time() - workload_metrics_last_collect_timestamp_seconds > 120` catches
  an exporter that has stopped;
- `increase(workload_vm_inspect_record_failures_total[1h]) > 0` means the
  egress record is incomplete;
- `increase(workload_vm_inspect_credential_unauthorized_total[1h]) > 0`
  means a provider is refusing a brokered key;
- `workload_health == 0` is a container whose health check is failing.

## The operations log

Every command that changes a workload adds one JSON line to
`/var/lib/workloads/<name>/operations.log`. The line records what the
command did to the workload: the image it moved from and to, whether it
rolled back, which archive it wrote. The journal shows only that someone
ran the command.

```console
$ sudo tail -1 /var/lib/workloads/web/operations.log | jq
{
  "ts": "2026-10-28T03:15:02Z",
  "command": "update",
  "ok": true,
  "user": "alice",
  "user_source": "login",
  "workload": "web",
  "kind": "container",
  "result": "rolled-back",
  "verify": "crashed",
  "images": {
    "web": {
      "image": "registry.example.com/web:2",
      "old": "sha256:1f2e3d4c5b6a",
      "new": "sha256:9a8b7c6d5e4f"
    }
  }
}
```

A line is the command's `--json` result for that workload, plus a timestamp
in UTC, the command, whether it succeeded, and who ran it. `user_source`
says where the name came from:

- `login` is the kernel's record of who logged in. It survives `sudo` and
  `su`, and a process cannot change it;
- `sudo` is `$SUDO_USER`, used when the kernel keeps no such record;
- `system` means no login session was behind the command, as with a timer or
  a systemd unit.

The lifecycle commands write here, and so do `create`, `init`, `duplicate`,
`install`, `edit`, `backup`, `restore` and a `cp` into a workload. A command
that changed nothing writes nothing: a `--dry-run`, `rollback --list`, or an
`update` that found the image already current. `secret` and `cleanup` never
write here, because neither belongs to one workload.

Lines start with the time, so `cat /var/lib/workloads/*/operations.log |
sort` gives a timeline for the whole host. The log is a record and not an
audit trail: root can edit it. `backup` leaves it out, so a restore does not
bring in another host's history, and `disable --purge` deletes it with the
rest of the workload. A line that cannot be written produces a warning,
never a failed command. The file is not rotated, and it gains only one line
per real change.

## Drift

```bash
sudo workloadctl drift
sudo workloadctl drift web
```

`drift` generates every workload's units into a scratch directory and
compares them with the ones in `/run/systemd/system/`. It prints a unified
diff for each file that differs, and exits 1 if anything does. When nothing
differs, it says so and exits 0. It changes nothing. Drift comes from a TOML
edited but not applied, from an upgrade that changes what workloadctl
generates, and from units left behind when a workload's marker or TOML was
removed by hand. `recreate` fixes the first two. Units left behind are
removed by `disable`, while the TOML is still there, or by the next boot.
`--json` prints the differences as JSON.

`drift` also compares each filtered workload's egress policy, as its
inspector loaded it at start, with the policy its TOML gives now. For one
that differs, `drift` prints the command that reloads it. Run `drift` as
root: the loaded policies are readable only by root and the workload, and a
non-root run cannot see them.

The warnings from `status` are a quicker, rougher check. The first means the
TOML is newer than the units. The second means the units were generated by a
different build of workloadctl. `drift` compares the contents, and ignores
which build wrote them.

## Cleaning up

```bash
sudo workloadctl cleanup
sudo workloadctl cleanup --apply
```

`cleanup` finds state whose workload no longer has a TOML under
`/etc/workloads.d/`:

- `_wl-*` users;
- directories under `/var/lib/workloads/`;
- loaded `wl_*` SELinux policy modules that no TOML declares.

A workload that is only disabled still has its TOML, so `cleanup` never
touches it. Without `--apply`, `cleanup` lists what it found and changes
nothing. With `--apply`, it removes each orphaned user and its ID ranges,
the user's whole directory under `/var/lib/workloads/` and its egress CA,
and the orphaned modules. The backups directory is never treated as an
orphan.

`cleanup` is for state that outlived its TOML. To remove a workload you
still have a TOML for, run `disable --purge` first and delete the directory
afterwards. `disable --purge` takes away more: the egress record, the
workload's entries in the host's firewall sets, and its runtime files.

### State from another bootc deployment

On a bootc host, `/etc` belongs to each deployment and `/var` is shared by
all of them. After a `bootc rollback`, the deployment you boot can lack a
workload's TOML and user while its data under `/var/lib/workloads/` is still
there. That looks exactly like an orphan, though the deployment you left
still owns it.

Each workload's directory therefore holds a `provenance.json`, which names
the deployment that last provisioned the workload. The workload rewrites it
at every start if it has changed. When that deployment still exists and is
not the one booted, `cleanup` leaves the state alone and lists it under
"State from another deployment — not swept". To delete it for good, boot
that deployment and run `disable --purge` there. State stamped with the
booted deployment, with one that no longer exists, or with no stamp at all
is judged as usual. On a host that is not bootc, no stamp is written.
`status --json` reports the stamp as `state_deployment`.
[ADR 005](../adr/005-var-state-deployment-provenance.md) records the rule
and its edge cases.

If you enable the workload again on the deployment that lacks its user,
workloadctl gives the new user the UID that owns the existing data, when
that UID is free, so the files stay readable.

## When something is wrong

```bash
sudo workloadctl doctor web
sudo workloadctl diagnose web
sudo workloadctl health web
```

`doctor` is the first look. In one report it shows the following:

- this boot's messages from unit generation;
- the state of each of the workload's units, with a journal excerpt for any
  that has failed or restarted;
- the setup checks;
- drift;
- health;
- for a filtered workload, its inspector's counters.

A unit that is active but has restarted counts as a problem, because a
restart loop otherwise looks healthy. `doctor` exits 0 when it finds nothing
and 1 when it finds anything. `diagnose` runs only the setup checks (the
user, ID ranges, linger, SELinux labels and, for a filtered workload, the
egress plumbing), each with a fix when it fails. `health` is the probe
described in [Health checks](04-containers.md#health-checks).
[Troubleshooting](10-troubleshooting.md) takes it from there.

## Working in a workload's podman

Each container workload has a podman of its own, run by its own user.
`incant` runs a podman command there, with the user, runtime directory and
session bus already set:

```bash
sudo workloadctl incant web -- ps -a
sudo workloadctl incant web -- images
sudo workloadctl incant web -- healthcheck run workload-web
sudo workloadctl incant web -- system df
```

Containers are named as their log identifiers are: `workload-<name>`, or
`workload-<name>-<container>` in a multi-container workload. For a VM,
`incant` sends one command to QEMU's monitor instead
([Getting into the guest](05-vms.md#getting-into-the-guest)). Every
`key=value` argument is passed as a string.

`incant` works around the TOML, not through it. Nothing it changes is
recorded in the TOML or in the operations log. A container you start by hand
is not supervised by systemd, and the next `recreate` or reboot puts back
whatever the units describe. Use it to look, and to do what the other
commands cannot, such as creating a named network or tagging a snapshot.
For anything inside a container, use `exec` and `shell`.
